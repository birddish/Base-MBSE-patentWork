# Mode: document — 专利文本技术建模与多文件对照

## 适用范围

对正式专利文本进行证据受控的 MBSE 建模，输入包括：
- 申请文件（权利要求书、说明书、附图）
- 引用对比文件（D1、D2……）
- 审查意见通知书 / 驳回决定中的审查员逻辑

本 mode 吸收自 `patent-text-mbse-rapid-modeling`，统一使用 R/F/S/B/E 五层模型。在此基础上增加两项 **强制补充分析**（不作为独立模型层）：
- **接口与上下文分析**（继承原 C 的功能）：系统边界、外部实体、接口卡
- **约束与参数分析**（继承原 P 的功能）：数值范围、阈值、配比、时序约束账本
这两项分析从 R/F/S/B/E 节点中提取和结构化，专用于支撑 OA 答复中的「对比文件不兼容」论证和「区别特征/预料不到效果」论证。

## 核心原则

1. **证据受控**：每个节点必须有来源定位和证据标签（D/I/Q/X，不含 N）
2. **文件独立**：先对每份文件单独完成模型，再建立跨文件对照表
3. **不得补全**：不得以文字相似性补足未公开的结构、接口、时序、因果或技术效果
4. **不得作法律结论**：不得输出新颖性、创造性或侵权的确定性结论

## 工作流程（六步骤）

### 步骤 1：登记文件与建模合同

| 字段 | 说明 |
|------|------|
| `file_prefix` | 文件前缀（如 `AP`、`D1`、`D2`） |
| `file_role` | 文件角色（申请文件/对比文件/审查意见/驳回决定） |
| `version_or_date` | 版本或日期 |
| `source_scope` | 可用范围（权利要求、说明书、附图） |
| `model_boundary` | 本轮模型关注的系统边界 |
| `known_missing_materials` | 已知缺失材料 |

### 步骤 2：建立术语与特征账本

为每份文件建立独立术语账本。不同文件的术语默认不等同。

| 字段 | 说明 |
|------|------|
| `node_id` | 文件前缀+编号 |
| `original_text` | 保留原文，不以总结替代 |
| `object` | 对象（名词/组件/数据） |
| `action` | 动作（动词/操作/转换） |
| `condition` | 条件（触发/守卫/约束） |
| `source` | 来源定位 |
| `evidence_level` | D/I/Q/X |
| `notes` | 备注 |

### 步骤 3：建立 R/F/S/B/E 五层模型

#### R（需求/约束）

技术问题、能力目标、工程约束或验收目标。以"如何……"开头。将约束性条件（原 P 节点中的数值阈值、逻辑约束等）作为 R 的子类型标注。

#### F（功能）

系统应完成的转换、判定、控制和数据处理。每个 F 节点应有明确的输入/输出和触发条件。

#### S（结构）

组件、模块、存储、通信链路及其组成关系。将上下文接口（原 C 节点）映射至 S：
- 外部实体 → S 中的"外部系统/用户/环境"节点
- 接口定义 → S 中的"接口/协议/连接"节点
- 输入/输出 → S 中标注流向的接口关系

#### B（行为）

活动、顺序、状态、事件、守卫条件、异常/超时分支。将交互行为（原 C 节点中的动态交互）映射至 B。

#### E（效果）

已实现或预期的技术效果。将数值效果（原 P 节点中的可测量指标）作为 E 的子类型标注。效果必须有明确的 S/B 支撑。

### 步骤 3A：接口与上下文分析（强制补充）

> **定位**：从五层模型中提取和结构化系统边界与接口关系。**不作为独立模型层**，产出的接口卡和上下文图直接供后续 Phase2（事实核实）和 Phase3（追溯链分析）引用。

#### 3A.1 系统边界定义

为每份文件明确定义系统边界：

| 字段 | 说明 |
|------|------|
| `system_under_analysis` | 被分析的系统/装置/方法 |
| `boundary` | 系统边界描述（哪些属于系统内、哪些属于系统外） |
| `external_entities` | 外部实体列表（用户、环境、上游/下游设备、网络、电源等） |
| `boundary_source` | 边界定义的原文依据 |

#### 3A.2 接口卡

对每个跨系统边界的交互建立接口卡。内部组件之间的关键接口也应记录：

| 字段 | 必填内容 |
|------|---------|
| `interface_id` | 接口编号 |
| `sender` | 发送方（S 节点或外部实体） |
| `receiver` | 接收方（S 节点或外部实体） |
| `object` | 传递对象（信号/数据/力/物料） |
| `direction` | 方向（单向/双向） |
| `trigger_or_guard` | 触发或守卫条件 |
| `medium_or_protocol` | 介质或协议（如已公开） |
| `is_cross_boundary` | 是否跨系统边界 |
| `source` | 来源定位 |
| `evidence_level` | D/I/Q |

#### 3A.3 多文件接口兼容性分析（用于 OA 答复）

对审查员主张的组合路径，逐项检查接口兼容性：

| 检查维度 | 问题 | 用于论证 |
|---------|------|---------|
| 系统边界冲突 | D1 的边界定义是否与 D2 的外部实体冲突？ | 「对比文件不兼容」论证 |
| 接口方向冲突 | D1 的接口方向能否适配 D2 的要求？ | 同上 |
| 触发条件冲突 | D1 的触发条件在 D2 的上下文中是否成立？ | 同上 |
| 协议/介质不兼容 | 两文件的接口协议或物理介质是否可互换？ | 同上 |
| 接口缺失 | 组合方案是否需要原文未公开的新接口？ | 「无技术启示」论证 |

### 步骤 3B：约束与参数分析（强制补充）

> **定位**：从五层模型中提取所有明确的数值约束、参数范围和逻辑条件。**不作为独立模型层**，产出的约束账本直接供 Phase2（事实核实——区别特征认定）和 Phase4（答复撰写——预料不到的技术效果）引用。

#### 3B.1 约束账本

| 字段 | 说明 |
|------|------|
| `constraint_id` | 约束编号 |
| `category` | 数值范围 / 阈值 / 配比 / 时序 / 几何 / 逻辑条件 / 材料限定 |
| `constraint` | 约束的具体内容（如 "60-80℃"、"A:B = 1:0.5-1:2"） |
| `related_R_node` | 对应的 R 节点（约束需求） |
| `related_E_node` | 对应的 E 节点（该约束产生的效果） |
| `source` | 来源定位（权利要求/段落/实施例） |
| `evidence_level` | D/I/Q |

#### 3B.2 多文件参数对比（用于 OA 答复）

| 对比维度 | 申请文件 | D1 | D2 | 重叠？ | 论证用途 |
|---------|---------|-----|-----|-------|---------|
| 温度范围 | 60-80℃ | 10-50℃ | — | ❌ 不重叠 | 区别特征认定 |
| 配比 | 1:0.5-1:2 | 1:3-1:5 | — | ❌ 不重叠 | 区别特征 + 预料不到效果 |
| 响应时间 | <100ms | <50ms | <200ms | ⚠️ D1 更优 | 不能用于区别论证 |

只填写原文明确记载的约束；空缺填「未公开」。

### 步骤 4：建立双向追溯链

#### 主链（正向）

```text
R → F → S → B/STATE → OutputState → E
```

`OutputState`是行为实现记录而非新增模型层。每一跳必须填写关系类型（`satisfy` / `refine` / `allocate` / `flow` / `trigger` / `guard` / `trace`）、来源定位、证据标签和前提/缺口。

#### 反向验证链

```text
B/S → F → R
```

验证每个结构/行为是否服务于某个功能/需求。

#### 双向追溯矩阵

| 字段 | 说明 |
|------|------|
| `chain_id` | 链编号 |
| `upstream` | 上游节点 |
| `relation` | 关系类型 |
| `downstream` | 下游节点 |
| `source` | 来源定位 |
| `evidence_level` | D/I/Q |
| `premise_or_gap` | 前提或缺口 |

**最低合格标准**：
- 至少一条显式主链
- 至少一条反向验证链
- 每一跳有关系类型、来源和证据标签
- 孤立节点、失败/超时/取消路径已标明原因或 Q
- 正常、失败、超时、取消等行为路径分别建链

#### 场景/状态表

| 字段 | 说明 |
|------|------|
| `scenario` | 场景名（正常/异常/超时/取消） |
| `trigger` | 触发条件 |
| `input_or_state` | 输入或当前状态 |
| `action` | 动作 |
| `output_or_next_state` | 输出或下一状态 |
| `source` | 来源定位 |
| `evidence_level` | D/I/Q |

未明确公开的场景行填 Q；不得以常识补足。

### 步骤 5：多文件对照

先完成每份文件的独立模型，再输出对照表。

| 关系 | 判定标准 |
|------|---------|
| **明确对应** | 两份文件均明确记载实质相同的对象、关系、条件和顺序 |
| **部分对应** | 对象或功能相近，但材料关系、接口、条件、顺序或效果至少一项缺失 |
| **未见明确对应** | 在已审阅材料中未找到明确记载；不表示技术上不能实现 |
| **待核实** | 文字、附图或版本不足以判断 |

#### 审查员逻辑映射

将审查意见中的主张映射至模型节点：

| 审查员主张 | 类型 | 对应节点 | 证据核对 |
|-----------|------|---------|---------|
| "D1 公开了 X" | 事实认定 | D1.Sx / D1.Bx | 待核实 |
| "D2 给出了 Y 的技术启示" | 启示认定 | D2.xx → AP.xx | 待核实 |

### 步骤 5A：OA权利要求评价台账与重建接口

进入审查意见答复交接时，必须在不改变各单文件独立模型的前提下生成下列台账：

```text
权利要求版本 → 有效引用路径 → TA → NB → IS/IC → OA问题 → 答复段落
```

1. 事实来源状态 `D/I/Q/X` 与文献新颖性、创造性法律资格分栏记录，不得相互替代；
2. 活动从属项按每条合法引用路径展开，至少形成 `full/inherited/no_separate_issue` 之一的NB和IS记录；
3. 权利要求修改后先计算影响闭包：直接修改项、全部引用后代及因编号、引用路径或主题变化受影响的权项；
4. 对闭包内对象重新生成TA及核心区别链，不能在旧TA上仅追加新节点；
5. 主修改策略冻结后只向活动快照输出一套台账；备选方案用独立集合和快照，禁止混入当前区别链。

### 步骤 6：质量门与输出

#### 质量门检查

| 检查项 | 通过条件 |
|--------|---------|
| 证据覆盖 | 每个节点均有来源定位和 D/I/Q/X 标签 |
| 追溯链完整性 | ①至少一条主链；②至少一条反向验证链；③每跳有关系类型、来源和标签；④孤立节点、异常路径已标明原因或 Q |
| 接口与上下文（3A） | 系统边界已定义；每个跨边界交互有接口卡；多文件接口兼容性分析已执行 |
| 约束与参数（3B） | 所有明确数值/范围/阈值已提取至约束账本；多文件参数对比表已完成 |
| 行为一致性 | 条件分支、超时、状态变化和异常路径不得超出原文；正常/异常路径分开表示 |
| 文件独立性 | 对照表不反向修改任何单文件模型；未公开不等于不可实现 |
| OA评价台账 | 活动权利要求及每条有效引用路径均有 TA→NB→IS/IC→OA→答复记录；全部活动记录引用同一快照 |
| 修改重建 | 修改影响闭包已计算，闭包内TA和区别链已经重建；旧评价记录已标失效 |

在写出"质量门通过"前，逐项回答：
- 主链的起点 R 和终点 B/S/E 是什么
- 每一跳的关系名称、来源和证据标签是什么
- 是否存在结构节点未分配功能、功能节点未落实到结构/行为、或行为节点未服务任何需求

#### 交付物清单

1. 文件登记表
2. 每份文件独立的 R/F/S/B/E 节点表
3. 每份文件独立的双向追溯矩阵
4. Mermaid 追溯链图（节点 ID 与表格一致）
5. 接口与上下文分析（系统边界 + 接口卡 + 多文件接口兼容性表）
6. 约束与参数分析（约束账本 + 多文件参数对比表）
7. 场景/状态表
8. 多文件节点对照总表
9. 审查员逻辑映射表（如适用）
10. 待核实问题表
11. Markdown 技术模型报告（用户确认后生成）
12. OA权利要求评价台账（如适用）

## 补充分析的使用方法

### 接口与上下文分析（3A）在 OA 答复中的使用

**核心论证模式**：「对比文件不兼容」——审查员主张 D1+D2 组合，但两文件的系统边界/接口/上下文不可调和。

**使用流程**：

```
步骤 3A 产出                          OA 答复中的引用
─────────────                         ────────────────
系统边界定义 ──────────────→  Phase2：核实审查员是否混淆了系统边界
接口卡         ──────────────→  Phase3：逐项对照 D1/D2 接口 → 识别冲突
多文件兼容性表  ──────────────→  Phase4：写入答复正文「D1 的系统边界为 X，
                                D2 要求的外部条件 Y 不在 D1 边界内，
                                若组合则需重新定义系统边界，
                                这不属于本领域技术人员的常规改进」
```

**典型论证场景**：

| 场景 | 接口分析发现 | 论证方向 |
|------|------------|---------|
| 机械 | D1 的驱动接口为齿轮啮合，D2 为摩擦驱动，接口物理不兼容 | 组合不可行 |
| 电子 | D1 的上下文为独立设备，D2 需要网络连接；组合需新增网络模块 | 无技术启示 |
| 软件 | D1 的 API 输入格式为 JSON，D2 期望 XML；组合需新增格式转换层 | 非显而易见 |
| 化学 | D1 的反应体系为无水条件，D2 的催化剂遇水失活；组合不可行 | 反向教导 |

### 约束与参数分析（3B）在 OA 答复中的使用

**核心论证模式**：「区别特征认定 + 预料不到的技术效果」——申请文件的参数范围与对比文件不重叠，且在该范围内取得了超出预期的效果。

**使用流程**：

```
步骤 3B 产出                          OA 答复中的引用
─────────────                         ────────────────
约束账本         ──────────────→  Phase2：逐项核对审查员对区别特征的认定
                                → 若审查员遗漏了参数差异 → 指出遗漏
多文件参数对比表  ──────────────→  Phase3：若 D1/D2 的参数范围与本申请不重叠
                                → 支持「区别特征成立」
                                → 进一步：若在特定参数范围内效果显著优于相邻范围
                                → 支持「预料不到的技术效果」
```

**参数对比表在答复中的直接引用示例**：

> 如模型约束与参数分析所示，本申请的温度范围为 60-80℃，D1 为 10-50℃，D2 未公开温度参数。两文件的温度范围不重叠。本申请在该温度范围内取得了产率提升 30% 的技术效果（参见 E3 节点，说明书[0045]），而 D1 在 10-50℃ 范围内未显示出该效果。因此，60-80℃ 的温度范围构成区别技术特征，且该参数选择产生了预料不到的技术效果。

### 与 R/F/S/B/E 模型的关系

```
                    R/F/S/B/E 五层模型（统一基础）
                           │
           ┌───────────────┼───────────────┐
           │               │               │
   disclosure mode    document mode    search mode
                           │
                   ┌───────┴───────┐
                   │               │
              3A:接口与上下文   3B:约束与参数
              （派生分析视图）  （派生分析视图）
                   │               │
                   └───────┬───────┘
                           ↓
              Phase2 事实核实 + Phase3 追溯链分析
                           ↓
              Phase4 OA 答复撰写
```

**数据来源**（不从零构建，从五层模型提取）：
- 3A 的系统边界 ← S 节点中的"外部实体"+"接口/连接"节点 + B 节点中的跨边界交互
- 3A 的接口卡 ← S 节点中的接口关系 + B 节点中的触发/守卫条件
- 3B 的约束账本 ← R 节点中的约束型需求 + E 节点中的数值效果 + S 节点中的规格参数
- 3B 的参数对比 ← 各文件的约束账本交叉对照
