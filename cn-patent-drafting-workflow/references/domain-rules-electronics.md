# 电子通信/AI/软件域撰写规则

## 规则成熟度说明

本文件为电子通信、AI、软件、算法、信号处理、网络、控制、天线、卫星及结构化数据领域的**已确立规则**。规则源自原 `ai-software-data-claims.md`，并扩展至更广泛的电子通信领域。

本域规则在阶段1至阶段5、阶段8及最终组卷时必读。

---

## 面向 CNIPA 的技术性链条

权利要求应体现：

1. 具体技术领域的输入数据。
2. 与该技术数据相关联的算法、模型或软件处理。
3. 算法特征与技术特征之间的功能性交互。
4. 具体技术领域的输出数据，或受控的技术对象。
5. 客观技术效果。

避免仅针对抽象数学模型、商业规则、展示规则或通用信息处理进行优化的权利要求。

## 算法与技术交互核查

仅在算法、软件或数据特征满足以下情形时，将其视为对权利要求有贡献的特征：

- 处理具有具体技术含义的数据，例如信号采样值、信道状态、天线参数、网络数据包、传感器读数、图像几何信息、深度图、设备状态、硬件参数或工程模型数据；
- 对技术对象施加约束或进行控制，例如终端、基站、天线、卫星载荷、机器人、建筑模型、BIM 对象、渲染管线、芯片、存储单元或网络节点；
- 改善技术指标，例如识别准确率、信号质量、时延、带宽、内存使用量、处理器利用率、模型执行效率、重建可靠性、标定准确性、同步准确性或几何一致性。

## 独立权利要求的清楚性规则

- 除非"融合结果""识别结果"或"模型输出"属于定义明确的外部产物，否则不要以 `获取融合结果`、`获取识别结果` 或 `获取模型输出` 起始。优选链条为：原始输入 → 解析/检测/估计 → 融合/选择/校验 → 结构化结果 → 最终输出。
- 若上游结果对于发明是必要的，应以必要的程度记载其生成过程。
- 仅记载为区别现有技术、解决技术问题所需的最少必要技术特征。
- 不得为增加特征数量或名义上提升新颖性、创造性而加入对技术问题没有贡献的实现细节。

## 术语转换表

在独立权利要求中使用体现技术含义的术语，并在说明书中对应实现名称。

| 实现表述 | 优选的权利要求表述 |
|---|---|
| field、key、JSON key | 信息、数据项、数据类别、数据结构 |
| API、endpoint、服务名称 | 处理模块、功能单元、接口模块 |
| 类名/函数名 | 模块、生成器、检测器、估计器、解析器、校验器 |
| 模型品牌/名称 | 模型类别或技术功能 |
| volumes | 体量信息/建筑体量信息 |
| connectors | 连接关系信息 |
| calibration | 空间标定信息 |
| modeling | 建模控制信息 |
| 墙体/门窗/材料/特征 | 建筑特征信息；在从属层级中细化为墙体信息、门窗信息和材料信息 |

## 权利要求分层模式

- 独立权利要求：概括性的技术类别和必要的数据流。
- 从属权利要求：子信息、校验规则、回退规则、置信度/质量评分、路径选择、下游工作流衔接、参数阈值、具体映射关系和实现变体。
- 系统独立权利要求：与对应方法独立权利要求的必要功能同构，不自动汇总全部方法从属特征或所有下游模块。
- 说明书实施例：字段名称、JSON 示例、API 名称、模型名称、服务名称、类名、脚本、UI 名称和工具链示例。

## 交底覆盖审查

对于 AI、软件或数据结构相关发明，在起草前分类每一个已披露技术模块，在完成不限项母版后再次复核分类、权利要求覆盖和省略理由。

将每个已披露模块分类为：

- 独立权利要求的必要技术特征；
- 从属权利要求的回退技术特征；
- 其他保护主题的技术特征；
- 仅实施例中的实现细节；
- 不纳入或待确认的技术特征及其理由。

下游工作流特征在具有交底支持并形成技术连续性时，在不限项母版中按不同技术主题建立独立从属分支，例如：

- 受结构控制的渲染；
- 局部重绘或局部修复；
- 基于模型架构的控制选择；
- 向工程软件导出数据；
- 与 BIM 或工程量计算的衔接；
- 以体现技术含义的层级表述 API、对象存储或数据库的衔接。

不得为压缩数量将彼此平行的编辑、渲染、局部重绘、BIM或工程导出分支强行合并。母版确认后，由代理师或用户选择提交候选版的保护主题分配；未设置`target_claim_count`时不得执行数字压缩，允许提交候选版按确认策略全部采用方法权利要求。

输出交底覆盖表：

| 审查阶段 | 已披露技术特征 | 交底证据 | 建议/实际层级 | 权利要求编号 | 纳入权利要求、实施例或省略的理由 |
|---|---|---|---|---|---|

## 术语映射输出

对于 AI、软件或数据相关案件，输出术语映射表：

| 权利要求术语 | 交底/实现术语 | 技术含义 | 建议层级 |
|---|---|---|---|

建议层级：独立权利要求、从属权利要求、实施例、避免使用。

## 客观技术效果

优先采用如下技术效果表述：

- 提高识别、重建、解析、标定、同步或融合准确性；
- 降低模型生成失败率或无效几何体比例；
- 提升设计、渲染、BIM、导出或控制模块之间的数据连续性；
- 降低数据存储、传输、计算、时延或硬件资源消耗；
- 提升网络吞吐量、信号质量、信道估计、天线匹配或干扰抑制能力；
- 提升系统内部性能或工程模型的可编辑性。

除非与可衡量的技术特征相关联，否则避免仅依赖 `智能化`、`体验更好`、`效率更高`、`美观` 或 `方便使用` 等表述。

## 结构化数据状态

结构化数据统一采用以下状态术语并说明转换条件：直接解析数据、标定数据、估算数据、补全数据、待校正数据。不得把估算、补全或待校正数据表述为已直接获取的确定性事实。

技术内容分开使用`fact_status=[D]/[I]/[Q]/[X]`和`drafting_status=[D]/[N]/[G]/[Q]/[X]`；其中N只由发明人或有权技术人员确认，G必须回指D或N，X不得进入申请文件。阶段8核验数据状态、处理规则和输出状态是否在权利要求、说明书和已有附图中一致。
