# 电子通信/AI/软件域撰写规则（审查意见答复）

## 规则说明

本文件为电子通信、AI、软件、算法、信号处理、网络、控制、天线、卫星及数据领域的域特定撰写规则。源自 `cn-patent-drafting-workflow` 的 `domain-rules-electronics.md` 并适配至审查意见答复场景。

## 电子通信域 S 节点类型与建模

### S 节点分类

电子通信域的权利要求 S 节点（技术特征）主要分为以下类型：

| S 节点类型 | 含义 | 审查意见中的典型争议 |
|-----------|------|-------------------|
| 硬件模块 | 处理器、存储器、传感器、天线、收发器、芯片等 | 是否被对比文件公开，是否为通用硬件 |
| 软件/算法模块 | 检测器、估计器、解析器、校验器、生成器、融合模块等 | 是否属于智力活动规则，是否具有技术性 |
| 数据项 | 信号采样值、信道状态、数据包、传感器读数、参数集等 | 数据是否有技术含义，是否为信息表述 |
| 信号/协议 | 信号格式、帧结构、调制方式、通信协议等 | 是否为标准协议，是否为惯用手段 |
| 处理步骤 | 接收、解析、检测、估计、融合、选择、输出等 | 步骤顺序是否为常规处理流程 |
| 技术参数 | 频率、功率、增益、时延、带宽、码率等 | 参数选择是否为常规优化 |

### 建模特别要求

- 对方法权利要求，将处理步骤序列作为 B 节点的时序关系；
- 对系统权利要求，将硬件模块与软件/算法模块的对应关系标注在 S 节点中；
- 对涉及数据处理的 F 节点，标注输入数据格式、处理算法、输出数据格式；
- 区分"技术特征"与"非技术特征"（商业规则、数学方法本身、信息表述本身），非技术特征标记为 X。

## 电子通信域审查意见常见问题

### 新颖性问题

- 审查员认为某算法步骤被对比文件公开 → 核实对比文件是否公开了相同的输入数据类型、处理逻辑和输出数据类型
- 审查员认为某硬件模块为通用计算机 → 论证该模块执行了特定的技术功能，而非通用数据处理

### 创造性问题

- **数据流断裂**：D2 的算法要求输入 [类型 X] 的数据，但 D1 系统输出 [类型 Y] 的数据 → 二者在数据接口上不兼容
- **协议/接口不兼容**：D1 使用协议 A，D2 的方案基于协议 B → 不能简单组合
- **算法-硬件不匹配**：D2 的算法依赖于 [特定硬件能力]，而 D1 的系统不具备该硬件 → 算法无法在 D1 上运行
- **信号处理链中断**：D2 的某处理步骤以 D1 的某中间结果为输入，但 D1 的该中间结果在 D1 的正常工作流程中不产生/不可得
- **技术领域分离**：D1 属于 [领域 X]，D2 属于 [领域 Y]，本领域技术人员在解决 [领域 X] 的问题时不会去 [领域 Y] 寻找方案

## 电子通信域特有的论证模式

### 面向 CNIPA 的技术性链条

权利要求的创造性论证应体现：

1. 具体技术领域的输入数据；
2. 与该技术数据相关联的算法、模型或软件处理；
3. 算法特征与技术特征之间的功能性交互；
4. 具体技术领域的输出数据，或受控的技术对象；
5. 客观技术效果。

### 算法与技术交互论证

仅在算法、软件或数据特征满足以下情形时，才将其作为对创造性有贡献的特征：

- 处理具有具体技术含义的数据（信号采样值、信道状态、天线参数、网络数据包、传感器读数等）；
- 对技术对象施加约束或进行控制（终端、基站、天线、芯片、存储单元或网络节点）；
- 改善技术指标（识别准确率、信号质量、时延、带宽、内存使用量、处理器利用率等）。

### 术语转换（审查意见答复适用）

在答复中，使用体现技术含义的术语：

| 审查员可能使用的表述 | 答复中应使用的技术表述 |
|-------------------|---------------------|
| "通用的数据处理" | "针对 [具体技术数据] 的特定处理，包括 [具体处理步骤]" |
| "常规算法" | "[算法名称] 在 [技术领域] 中的特定应用，解决了 [具体技术问题]" |
| "计算机程序本身" | "执行 [具体技术功能] 的 [模块名称]，该模块与 [硬件模块] 协同工作以 [技术效果]" |
| "信息表述" | "具有技术含义的 [数据类型]，其 [技术属性] 决定了 [技术结果]" |

## 电子通信域论证措辞规则

- 数据流断裂论证："D2 的处理方法以 [类型 X] 的数据为输入前提，而 D1 的系统在正常运行中输出 [类型 Y] 的数据。由于 [类型 Y] 的数据不具备 [类型 X] 所需的 [属性]，D2 的方法无法直接应用于 D1 的输出。本领域技术人员需要对 D1 的输出进行额外的 [转换/预处理] 步骤，但 D1 和 D2 均未公开此种转换。"
- 协议/接口不兼容论证："D1 的通信系统基于 [协议 A]，其帧结构/信号格式为 [格式 A]。D2 的方案针对 [协议 B] 设计，其依赖的 [特定字段/参数] 在 [协议 A] 中不存在。将 D2 的方案应用于 D1 需要对 [协议 A] 进行根本性修改，这超出了简单替换的范畴。"
- 算法-硬件不匹配论证："D2 的算法要求 [硬件支持 X]，而 D1 的设备仅具有 [硬件 Y]。在不改变 D1 硬件架构的前提下，D2 的算法无法执行其核心步骤 [步骤 Z]。"
- 技术领域分离论证："D1 涉及 [领域 X] 的 [具体应用场景]，其面临的技术问题是 [问题 X]。D2 虽然公开了类似的数据处理方式，但 D2 属于 [领域 Y]，解决的是 [问题 Y]。领域 X 与领域 Y 的技术环境、数据特征和性能要求存在本质差异，本领域技术人员没有动机跨越技术领域寻求解决方案。"

## 常见陷阱

- [ ] 不要将"计算机实现的"等同于具有技术性——需论证算法与技术数据的交互
- [ ] 不要仅以"提高了效率"作为技术效果——需具体说明提高了什么技术指标的效率
- [ ] 注意单一侵权主体——系统权利要求中各模块是否由同一实体实施
- [ ] 注意方法权利要求中各步骤的执行主体一致性
- [ ] 不要将权利要求撰写为纯功能描述——每个功能模块应有对应的技术实现基础
